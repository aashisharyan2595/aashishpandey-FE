NGINX HTTP/2 flaws let attackers run code: what to patch

Quick answer. Two critical NGINX HTTP/2 flaws, CVE-2026-123007 and CVE-2026-123633, can let an unauthenticated attacker run code on the server. Upgrade to NGINX 1.30.7 or 1.31.9, or turn HTTP/2 off until you can.

What happened?

On November 18, F5 shipped security updates for NGINX, the web server that Wiz says powers more than 225 million websites. Two of the fixes matter most. CVE-2026-123007 and CVE-2026-123633 are both flaws in how NGINX handles HTTP/2 traffic, and both can let an attacker run code on the server without logging in. Wiz rates each one critical, with a CVSS 4.0 score of 9.2.

Five research teams found them independently: Wiz Research, Ikotas Labs, Metnir, Rapid7 and Xint. Wiz says it reported CVE-2026-123633 to F5 on October 21, and that F5 told it another team had already reported the same bug. Hackread adds that Wiz used its own AI scanning platform to find the flaws, then checked the impact with Gemini 4 Carbon and ChatGPT 5.6 Sol.

What are the two flaws?

CVE-2026-123007 is an integer underflow in HTTP/2 flow control, per Wiz. It affects NGINX from version 1.9.5, released in 2015, up to 1.31.8, and the official NGINX advisory list gives the same range. Wiz showed code execution against a server that only served ordinary static files, with no backend app and no third-party modules.

CVE-2026-123633 is a use-after-free. It hits versions 1.19.7 through 1.31.8, and it needs NGINX to proxy requests to a backend. BleepingComputer explains the trigger: when the worker runs low on connection slots, it can close a live connection and free memory that a request is still using.

Both need HTTP/2 switched on for a listener an attacker can reach, and CVE-2026-123633 also needs proxying to a backend. Those conditions are the first things to check.

Why does it matter?

NGINX usually sits at the front door. One server often handles traffic for several sites and APIs, so a break-in there can reach all of them. Wiz points out that the flaws are in NGINX itself, so an app with clean code can still be exposed.

The fix list is longer than two bugs. F5's release closed ten NGINX vulnerabilities in all, including three more use-after-free flaws that Wiz's table also scores 9.2, in HTTP/3, the DNS resolver and the mail proxy module, plus a denial-of-service bug over TLS 1.3. If you run NGINX Open Source, the fixed versions are 1.30.7 on the stable branch and 1.31.9 on mainline.

How bad is it really?

The sources describe the risk differently.

Wiz says ASLR, the usual memory-safety defence, doesn't protect against these two, because an attacker can read memory before running code. F5's advisories, as summarised in a community post on F5's DevCentral, describe code execution as depending on ASLR being disabled or bypassed. The same post warns against treating ASLR as proof you're safe.

On exposure, Censys has a live tracker. BleepingComputer reports that about 8.8 million NGINX services were potentially exposed to CVE-2026-123007 as of November 19, judged by version and HTTP/2 support. More than 511,000 of those had already been patched or mitigated. Another 104 million NGINX services don't reveal their version, so nobody can say for them.

Xint reported that 98.9% of hosts showing a recognisable version fell in the affected range. That figure ignores whether HTTP/2 is on and whether a distribution backported the fix. Security researcher Florian Roth called the bugs worse than Node2Shell and Java2Shell but not an imminent threat for most deployments, since he says they are exploitable in non-default configurations. He also scanned a few hundred HTTPS endpoints and found roughly 66% supported HTTP/2. Wiz, for its part, lists CVE-2026-123007 as exploitable in default configurations with HTTP/2 enabled.

Then there's the root question. "NGINX2Root" is the name Xint gave to its research on five NGINX flaws and a separate Linux kernel flaw. In one demo, Xint chained an NGINX flaw with the kernel bug to get root and escape a Docker container. A community post on F5's DevCentral, summarising F5's advisories, makes the limit plain: the NGINX flaws give code execution with the worker's privileges, and root needs that extra step.

What should you do now?

  1. Find every NGINX you run: servers, containers, Kubernetes ingress, appliances from vendors that bundle it.
  2. Check whether HTTP/2 is enabled and whether the box is reachable from the internet.
  3. Upgrade to 1.30.7 or 1.31.9. For NGINX Plus, only 37.0.8.1 (the LTS track) and 37.3.0.1 (the continuous release track) fix both HTTP/2 flaws, according to Wiz's table and the F5 community post. The earlier 37.0.7.1 and 37.2.0.1 fix only CVE-2026-123633, so being patched for one CVE doesn't mean you're patched for both.
  4. If you can't upgrade yet, Wiz and Hackread both say to turn HTTP/2 off for now. On NGINX 1.25.1 or later, set http2 off; in the server block and drop the http2 parameter from listen lines. Test your app, reload, and confirm the old workers have exited. BleepingComputer notes that this only covers the two nginx2root HTTP/2 flaws, not the other fixes.
  5. On Linux distributions, look for the vendor's own patched package, because the community post notes that distribution packages carry their own fixed builds.
  6. In Kubernetes, check the image actually running in your pods. The community post says F5's NGINX Ingress Controller 2026-lts-r11 update moves NGINX Plus to 37.0.8.1, and other ingress projects that use NGINX have their own update paths.

If you use F5's BIG-IP, the community post says F5 lists it as not vulnerable to these two CVEs, across all modules. It adds that F5 Distributed Cloud and NGINX One Console were still under investigation when it was written.

What don't we know yet?

Severity labels differ by source. Wiz scores both flaws 9.2, while the official NGINX advisory list tags CVE-2026-123007 as major and CVE-2026-123633 as medium. BleepingComputer adds that Censys reproduced the memory corruption in four of the five flaws in lab tests but didn't get remote code execution.

None of the pages I read reported attacks in the wild. That could change quickly. Wiz says it isn't releasing its proof-of-concept exploit for CVE-2026-123633, but a SecurityWeek headline on its site says PoC exploits have gone public for the NGINX2Root flaws, and I haven't seen the details. Whether the real number of exposed servers is closer to Censys's version count or Roth's configuration view is also open.

What to watch

Watch for the first confirmed exploitation report, for your distribution's patched package, and for F5's update on its cloud products. Wiz makes the point that the gap between disclosure and exploitation is getting shorter, so patching speed matters most.

This isn't the first NGINX scare this year. In June, SecurityWeek covered two other critical NGINX bugs, CVE-2026-42530 and CVE-2026-42055, that could crash a worker and allow code execution only if ASLR was disabled or bypassed.

My take

I'd treat this as a this-week job, not a panic. If you run NGINX on the open internet with HTTP/2 on, patch it first, or switch HTTP/2 off today as a stopgap. If your NGINX sits behind something that speaks only HTTP/1.1 to it, you have a little breathing room, but I'd still schedule the upgrade, because the community post calls that kind of architecture reasoning, not an F5-validated mitigation. And for a small team without a server inventory, the real lesson is to build one before the next advisory lands.

Frequently asked questions

Which NGINX versions are affected by the HTTP/2 flaws?

CVE-2026-123007 affects NGINX from 1.9.5 through 1.31.8. CVE-2026-123633 affects 1.19.7 through 1.31.8 and needs NGINX to proxy requests to a backend. Both need HTTP/2 enabled on a listener an attacker can reach. The fixed releases are 1.30.7 on the stable branch and 1.31.9 on mainline.

How do I protect NGINX if I can't upgrade yet?

Wiz and Hackread both say to turn HTTP/2 off temporarily. On NGINX 1.25.1 or later, set http2 off in the affected server blocks and remove the http2 parameter from listen directives. Test your app, reload NGINX, and confirm the old workers exited. BleepingComputer notes this only covers the two HTTP/2 flaws, so upgrade as soon as you can.

Do these NGINX flaws give attackers root access?

Not on their own. A community post summarising F5's advisories says the NGINX flaws allow code execution with the worker process's privileges, and getting root needs an extra privilege escalation step. Xint demonstrated chaining one flaw with a separate Linux kernel bug to escape a Docker container and gain root, but that is a second vulnerability.

Is F5 BIG-IP affected by CVE-2026-123007 and CVE-2026-123633?

The F5 advisories, as summarised on DevCentral, list BIG-IP, across all modules, as not vulnerable to these two CVEs within the software it evaluated. NGINX Open Source and NGINX Plus have vulnerable releases. F5 Distributed Cloud and NGINX One Console were listed as under investigation when the F5 community post was written, so check the current advisory.

Are the NGINX HTTP/2 flaws being exploited in the wild?

None of the pages I read reported attacks in the wild. Wiz says it isn't releasing its proof-of-concept for CVE-2026-123633, though a SecurityWeek headline says proof-of-concept exploits have gone public. Patch internet-facing servers first.
